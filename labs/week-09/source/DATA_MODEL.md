## 1. ภาพรวม

ระบบนี้ใช้โครงสร้างความสัมพันธ์แบบ หนึ่งต่อหลาย (One-to-Many หรือ 1:N)

ผู้ใช้งาน 1 คน (users) สามารถสร้างคำร้อง (requests) ได้หลายรายการ

คำร้องแต่ละรายการ (requests) จะถูกส่งโดยผู้ใช้งานเพียงคนเดียวเท่านั้น ผ่าน Foreign Key requester_id ที่ชี้ไปยัง users.id
 
 ┌───────────────────────┐             ┌───────────────────────────────────┐
│         users         │ 1         N │             requests              │
├───────────────────────┤             ├───────────────────────────────────┤
│ id (PK)   INTEGER     │◀────────────│ requester_id (FK) INTEGER         │
│ name      TEXT        │             │ id (PK)           TEXT            │
│ department TEXT       │             │ request_type      TEXT            │
│ email     TEXT (UQ)   │             │ location          TEXT            │

                                      │ priority          TEXT            │
                                      │ status            TEXT            │
                                      │ created_at        TEXT            │

## 2. ทำไมต้องแยกเป็น 2 ตาราง

> **ข้อนี้สำคัญที่สุด** — ผู้สอนจะอ่านข้อนี้เป็นหลัก
ถ้าสมชายเปลี่ยนชื่อ ต้องแก้กี่ที่?
ตอบ: แก้เพียง 1 ที่เท่านั้น คือแถวข้อมูลของสมชายในตาราง users แล้วประวัติคำร้องทั้งหมดของสมชายจะแสดงชื่อใหม่ทันทีเมื่อทำคำสั่ง JOIN

ปัญหาจากการเก็บ requesterName รวมไว้ในทุกคำร้อง (แบบ Week 06–07)
ข้อมูลซ้ำซ้อน (Data Redundancy): หากผู้ใช้คนเดิมส่งคำร้อง 10 ครั้ง ชื่อ สังกัด และอีเมลจะถูกบันทึกซ้ำถึง 10 รอบ สิ้นเปลืองพื้นที่จัดเก็บโดยใช่เหตุ

แก้ไขไม่ครบถ้วน (Update Anomaly): หากผู้ใช้เปลี่ยนชื่อหรือย้ายแผนก แล้วระบบอัปเดตข้อมูลในตารางคำร้องไม่ครบทุกแถว จะเกิดข้อมูลขัดแย้งกันในระบบ (เช่น บางคำร้องเป็นชื่อเก่า บางคำร้องเป็นชื่อใหม่)

พิมพ์ผิดแล้วไม่มีใครรู้ (Data Inconsistency): การกรอกชื่อเป็นข้อความอิสระทำให้ตรวจสอบความถูกต้องได้ยาก หากสะกดต่างกันแค่วรรคเดียวหรือตัวสะกดเดียว ระบบจะมองว่าเป็นคนละคน ทำให้สถิติการแจ้งงานผิดพลาด

เก็บข้อมูลเพิ่มไม่ได้หากยังไม่มีคำร้อง (Insertion Anomaly): หากมีบุคลากรหรือนักศึกษาใหม่เข้ามาในระบบแต่ยังไม่เคยแจ้งเรื่องซ่อม ระบบเดิมจะไม่สามารถเก็บรายชื่อของบุคคลนั้นไว้ได้เลย เพราะต้องรอให้เกิดคำร้องขึ้นมาก่อน

การแยกตารางช่วยแก้ปัญหาอย่างไร
การแยกตารางตามหลัก Normalization ทำให้ตาราง users ทำหน้าที่เป็นศูนย์กลางข้อมูลผู้ใช้งานจุดเดียว (Single Source of Truth) ช่วยตัดปัญหาข้อมูลซ้ำซ้อน รักษาความถูกต้องสมบูรณ์ของข้อมูล (Data Integrity) และสามารถเพิ่มหรือแก้ไขข้อมูลผู้ใช้งานได้เป็นอิสระจากประวัติคำร้อง

## 3. รายละเอียดตาราง

ตาราง users (เก็บข้อมูลผู้ใช้งาน)

| คอลัมน์ | ชนิด | ข้อกำหนด (Constraints) | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | `เป็น Surrogate Key ที่สร้างตัวเลขลำดับอัตโนมัติ รวดเร็วต่อการค้นหาและทำ Index` |
| `name` | TEXT | NOT NULL | `ชื่อ-นามสกุลของผู้ใช้งาน เป็นข้อมูลจำเป็น ห้ามเป็นค่าว่าง` |
| `department` | TEXT | NOT NULL | `สังกัด/ภาควิชา เพื่อใช้ระบุฝ่ายและจัดกลุ่มรายงานสถิติ` |
| `email` | TEXT | NOT NULL | `ใช้อีเมลเป็นบัญชีระบุตัวตน ต้องมีข้อมูลเสมอและห้ามซ้ำกันในระบบ` |

ตาราง requests (เก็บรายการคำร้อง)

| คอลัมน์ | ชนิด | ข้อกำหนด (Constraints) | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY  | `ใช้รหัสเชิงความหมาย เช่น REQ-001 เพื่อให้ผู้ใช้และช่างสื่อสารติดตามงานได้เข้าใจง่าย` |
| `requester_id` | INTEGER | NOT NULL, FOREIGN KEY REFERENCES users(id) | `เชื่อมโยงกลับไปยังผู้แจ้งในตาราง users และบังคับว่าทุกคำร้องต้องมีผู้รับผิดชอบ` |
| `request_type` | TEXT | NOT NULL, CHECK (request_type IN (...)) | `จำกัดประเภทคำร้องให้ตรงตามที่ระบบรองรับ ป้องกันการบันทึกข้อมูลที่ไม่ถูกต้อง` |
| `location` | TEXT | NOT NULL | `ระบุสถานที่เกิดปัญหา เพื่อให้เจ้าหน้าที่เข้าดำเนินการได้ถูกจุด` |
| `details` | TEXT | NOT NULL | `อธิบายรายละเอียดปัญหาหรือความต้องการใช้งาน` |
| `priority` | TEXT | NOT NULL, CHECK (request_type IN (...)) | `กำหนดระดับความสำคัญ เริ่มต้นที่ normal เพื่อจัดลำดับคิวงาน` |
| `status` | TEXT | NOT NULL | `กำกับกระบวนการทำงาน เริ่มต้นที่ pending จนกระทั่งจบงาน` |
| `created_at` | TEXT | NOT NULL DEFAULT (datetime('now', 'localtime')) | `ใบันทึกวันเวลาที่สร้างรายการอัตโนมัติ สำหรับจัดเรียงลำดับเวลาล่าสุด` |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

1. ทำไม users.id กับ requests.id จึงใช้ชนิดต่างกัน (INTEGER กับ TEXT)?
users.id ใช้ INTEGER: เป็นคีย์ภายใน (Internal Key) มีจุดประสงค์เพื่อให้คอมพิวเตอร์ประมวลผล การใช้เลขจำนวนเต็มทำให้การจับคู่คำสั่ง JOIN ทำงานได้เร็วที่สุดและกินพื้นที่จัดเก็บบนดิสก์น้อย

requests.id ใช้ TEXT: เป็นรหัสทางธุรกิจ (Business Identifier) ที่ต้องสื่อสารกับผู้ใช้งานโดยตรง การมีตัวอักษรนำหน้า เช่น REQ- ช่วยให้แยกประเภทเอกสารได้ชัดเจน ไม่สับสนกับตัวเลขลำดับอื่นในระบบ

2. ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว?
การกำหนดข้อกำหนดในระดับฐานข้อมูลใช้หลักการ Defense in Depth (การป้องกันหลายชั้น):

ฝั่ง API หรือ Frontend อาจเกิดข้อผิดพลาดทางโปรแกรม (Bug) หลุดรอด หรืออาจมีผู้ไม่หวังดียิงข้อมูลข้าม Controller เข้ามา

ในชีวิตการทำงานจริง อาจมีการรัน SQL Script โดยตรงเพื่อแก้ไขข้อมูล หรือมี Service อื่นมาเชื่อมต่อฐานข้อมูลร่วมกัน

ฐานข้อมูลคือปราการด่านสุดท้าย การใช้ CHECK constraint จะเป็นหลักประกันว่าข้อมูลที่บันทึกลงดิสก์มีความถูกต้องตามกฎเกณฑ์เสมอ 100%

## 5. ตัวอย่างการใช้ JOIN


SELECT 
  r.id AS request_id,
  u.name AS requester_name,
  u.department,
  r.request_type,
  r.priority,
  r.status
FROM requests r
JOIN users u ON r.requester_id = u.id
ORDER BY r.id ASC;

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

ผลลัพธ์ที่ได้จากคำสั่ง JOIN ใน SQL:
REQ-001 | สมชาย ใจดี | pending

ข้อมูล JSON ที่ API ส่งให้ React (Week 07):
```json
{
  "id": "REQ-001",
  "requesterName": "สมชาย ใจดี",
  "status": "pending"
}

ข้อสังเกตที่พบ
Frontend ต้องการข้อมูลแบบ Flat: หน้าเว็บ React ต้องการข้อมูลในรูปแบบ Object ที่มีฟิลด์ requesterName รวมอยู่ทันทีเพื่อนำไปเรนเดอร์ลง UI โดยตรง ไม่จำเป็นต้องรู้ว่าข้อมูลถูกแยกเก็บในฐานข้อมูลอย่างไร

บทบาทของ Backend ในสัปดาห์ที่ 10: Backend API ทำหน้าที่เป็น ตัวกลางประสานโครงสร้าง (Adapter/Transformer) โดยฝั่งฐานข้อมูลจัดเก็บแบบ Normalization (2 ตาราง) เพื่อความปลอดภัยและลดความซ้ำซ้อน จากนั้น Backend จะเขียน SQL JOIN ข้อมูล และแปลงโครงสร้างแถวข้อมูลให้กลายเป็น Flat JSON รูปแบบเดิมที่ Frontend เคยใช้งาน
